# The `benchctrl` command line

Every MCP tool is a shell command. 324 of them, across nine groups:

```bash
benchctrl adu218 relay-states
benchctrl sdm4065a measure-dc-voltage
benchctrl --remote unoq.local dp2031 info
```

The shape is always `benchctrl [global flags] <group> <command> [args]`.

Nothing here is hand-written per device. The subcommands are generated by
reflection over each driver's `_TOOLS` tuple — the same tuple the MCP server
registers — so a tool added to a driver becomes a shell command with no edit to
the CLI. What is *not* generated is anything to do with risk or lifecycle; see
[Authorisation](#authorisation) and [Why a one-shot needs its own
lifecycle](#why-a-one-shot-needs-its-own-lifecycle).

## The groups

| group | device | commands |
|---|---|---|
| `arc` | Otii Arc / Arc Pro source-measure unit | 23 |
| `qr10x` | Eastwood QR10x programmable resistance standard | 11 |
| `dl3031a` | Rigol DL3031A electronic load | 45 |
| `dp2031` | Rigol DP2031 triple-output supply | 134 |
| `sdm4065a` | Siglent SDM4065A digital multimeter | 54 |
| `pdu41002` | CyberPower PDU41002 switched PDU (switches mains) | 15 |
| `cp2112` | SiLabs CP2112 GPIO / DUT reset lines | 10 |
| `adu218` | Ontrak ADU218 relays, inputs, counters and watchdog | 19 |
| `framework` | recording I/O and battery analytics (no device needed) | 13 |

`benchctrl <group> --help` lists a group's commands; `benchctrl <group> <command>
--help` prints the tool's own docstring, which is the same text a model sees.

### The legacy Arc commands

Ten commands predate all of this and are Arc-only: `discover`, `info`,
`set-voltage`, `set-output`, `set-range`, `set-current-limit`,
`set-exp-voltage`, `set-gpo`, `capture`, `stream`. They still work exactly as
[`getting_started.md`](getting_started.md) documents, and they still open the Arc
directly — so `--remote` and `--sim` do **not** apply to them, and neither does
the authorisation model below. Prefer `benchctrl arc …` for anything new.

`benchctrl set-voltage 3.3` and `benchctrl arc set-voltage 3.3` are different
commands reaching the same instrument. That is not an accident worth cleaning up
until the legacy ten are removed.

## Authorisation

Reads run unannounced. Anything that changes what the hardware is doing needs
you to say so, in one of two ways, and the requirement is a property of the
command rather than something inferred from its name.

```bash
benchctrl adu218 relay-states                  # a read
benchctrl adu218 set-relay-state 0 on          # refused: needs --yes
benchctrl --yes adu218 set-relay-state 0 on    # runs

benchctrl --yes adu218 set-watchdog 3          # still refused: needs the env gate
BENCHCTRL_ADU218_ARM_WATCHDOG=1 benchctrl --yes adu218 set-watchdog 3
```

`--help` marks them, so you can see which commands move hardware before typing
one: `[!]` needs `--yes`, `[!!]` needs `--yes` **and** a named environment
variable.

Four tiers, in [`cli_tiers.py`](../src/benchctrl/cli_tiers.py), with every one of
the 324 tools classified explicitly and a test asserting completeness in both
directions:

- **read** — no gate.
- **tier 2 — no confirmation.** Setpoints on a de-energised output, ranges, NPLC,
  and deliberately the *de-energising* direction: `adu218 reset-relays`,
  `cp2112 reset-lines`. Moving toward the safe state is frictionless on purpose.
  A test asserts de-energising is never gated harder than energising — if
  reaching safety needed more ceremony than leaving it, an operator fighting a
  live output would have a gate in the way.

  `set-voltage` is here too. Requiring `--yes` for every setpoint would make the
  flag reflexive, and a confirmation nobody reads protects nothing.
- **tier 1 — `--yes`.** Energising, sinking, closing a relay contact, driving a
  line into a DUT.
- **tier 1 + env gate — `--yes` and a named variable.** For operations whose
  consequence outlives the command:

  | variable | what it authorises |
  |---|---|
  | `BENCHCTRL_PDU_ALLOW_SWITCHING=1` | `pdu41002 set-outlet-state`, `pdu41002 reset-outlet` |
  | `BENCHCTRL_ADU218_ARM_WATCHDOG=1` | `adu218 set-watchdog` |

  The two are separate variables because one authorisation must not grant the
  other. `--yes` says you meant to run a command; the variable says you know
  what is physically attached. Those are different claims.

  `set-watchdog` earns its own gate: `WDn` sets *and arms* in one command, and
  the relay opens later, after the CLI has exited. `set-outlet-state` earns its
  own because it switches mains.

An environment variable is a weak gate on its own — a `.bashrc` export satisfies
it permanently and invisibly — which is why it is always the *second* factor and
never the only one.

### The classification is not `is_mutator()`

The agent gates remote calls on `dispatch.is_mutator()`, a name-prefix match.
Reusing it here would have been the obvious move and is wrong:

```python
>>> dispatch.is_mutator("write")            # raw SCPI passthrough
False
>>> dispatch.is_mutator("take_snapshot")    # samples, changes nothing
True
>>> dispatch.is_mutator("step_voltage_up")  # moves a live output
False
```

`write` and `query` exist on all three SCPI drivers and are arbitrary-command
escape hatches. A CLI keying its read/write split on that predicate would file
raw SCPI under "safe". They are tier 1 here, and a test asserts `is_mutator`
still disagrees — so if the drivers are ever renamed to `write_raw`, the test
fails and tells you the table can be simplified.

### Arguments deliberately not exposed

Some tool parameters are withheld, and `--help` says so under *"Deliberately not
exposed"* with the reason. An operator who cannot find a flag deserves to know
it was withheld on purpose rather than forgotten.

- **`verify`** — defaults `True` on both switching drivers and is load-bearing:
  the ADU218 reports no error, ever (`KNOWN_LIMITATIONS.md` §F-21), so
  `verify=False` returns the value you *commanded*, not the one the device is
  at. Verification is not a preference.
- **`allowed_relays` / `allowed_outlets` / `panic_outlets`** — safety
  allowlists. A flag would let a caller *widen* scope per invocation, inverting
  their purpose. They come from config (below), which describes this bench's
  cabling: stable, reviewable, diffable, and out of shell history.
- **`allow_alternate_function`** (CP2112) — an operator attestation the MCP
  layer already removed, on the grounds that it is a bench observation rather
  than something a caller can establish.

## Modes: local, sim, remote

Three flags bind devices, per device key, before anything opens:

```bash
benchctrl --sim ontrak_adu218 adu218 relay-states       # a simulator
benchctrl --remote unoq.local:9737 adu218 relay-states  # a bench agent
benchctrl --remote unoq.local --local otii_arc arc info # split bench
```

`--local` and `--sim` are repeatable; `--remote` takes `HOST[:PORT]`. Any
non-local binding is announced on stderr, so *"why did that read a simulator"*
has an answer:

```
$ benchctrl --sim ontrak_adu218 adu218 relay-states
benchctrl: ontrak_adu218 -> sim
mask: 0
...
```

Silence means every device resolved local. A line per device would train you to
ignore the one that matters.

Precedence and the config file are documented in [`remote.md`](remote.md); the
CLI flags sit at level 2. With no flags the CLI passes no config at all, so the
environment and `~/.config/benchctrl/config.json` keep their documented
priority — an empty config object would otherwise count as an override and beat
them both.

A config that cannot be read, or that names an invalid mode, **exits non-zero
and says so**. It never degrades to "no config", because that resolves every
device local, and a device you asked to *simulate* would then drive the real
instrument.

### Per-bench open arguments

The open is implicit — `benchctrl pdu41002 outlet-states` should not require you
to type an open command first — and its arguments come from the `open` block of
`~/.config/benchctrl/config.json`, the same dict the MCP server and the agent
already forward:

```json
{
  "devices": {
    "cyberpower_pdu41002": {
      "mode": "local",
      "open": {"port": "/dev/benchctrl/pdu41002", "allowed_outlets": [4, 5]}
    }
  }
}
```

One file, not a second CLI-only one: two files would eventually disagree about
which outlets are allowed.

**Never put a password there.** `DeviceConfig.to_dict()` emits `open` verbatim,
and `open` crosses the RPC wire, which is authenticated but not encrypted. The
PDU password comes from `BENCHCTRL_PDU_PASSWORD` in the environment where the
*driver* runs — on the board, for a remote bench.

## Exit codes

The contract with a shell script:

| code | meaning |
|---|---|
| 0 | the command ran |
| 1 | the command ran but found nothing (`discover` with no SMU) |
| 2 | the device or the library refused |
| 3 | the CLI refused: a missing `--yes` or env gate |
| 4 | the command ran, but teardown could not de-energise |
| 130 | interrupted |

2 and 3 are distinct so a script can tell *"the device is not there"* from
*"you did not authorise this"*. A refusal happens before anything is configured
or opened, and says so: `Nothing has been sent to the device.`

**Code 4 exists because the alternative is silent.** `dl3031a_close` disables
the load input and `dp2031_close` disables three outputs; both report a *failed*
de-energise as a key in their result dict rather than as an exception, so the
close itself still completes. A CLI checking only for exceptions would print
your measurement and exit 0 with the load still sinking current. So:

```
$ benchctrl dl3031a measure-voltage
volts: 3.3
benchctrl: teardown could not return the device to its safe state
(input_off_failed: ...). An output may still be energised or sinking current —
check the instrument's front panel before touching the DUT.
$ echo $?
4
```

The measurement still prints, and the warning goes to stderr so `--json` stays
parseable. Losing the reading to a teardown problem would make the CLI unusable
exactly when the bench is misbehaving.

## Output

Default is a flat listing; `--json` emits the raw result:

```bash
$ benchctrl adu218 relay-states
relays: 0=on, 1=off, 2=on, 3=off, 4=off, 5=off, 6=off, 7=off
energised: 0, 2
mask: 5

$ benchctrl --json adu218 relay-states
{
  "relays": {
    "0": true,
    "1": false,
    ...
  },
  "energised": [0, 2],
  "mask": 5
}
```

Booleans render as `on`/`off` rather than `True`/`False`, because a one-shot
command whose answer is "is outlet 4 live" should read like an answer. That
holds one level down too, which is where it matters most — the per-channel reads
return a dict, so `relays` is exactly the value that needs it:

```bash
$ benchctrl adu218 input-states
ports: A=[off, off, off, off], B=[off, off, off, off]
mask: 0
```

Collections one level down are bracketed because the separators would otherwise
merge; at the top level the key already delimits.

`-v` logs at INFO to stderr, which is how you see a teardown failure on the
exception path, where the warning is dropped in favour of the original error.

## on/off arguments

Boolean parameters take a word, never a flag, and the word is checked:

```bash
benchctrl --yes adu218 set-relay-state 0 off     # False
benchctrl --yes adu218 set-relay-state 0 disable # also False
benchctrl --yes adu218 set-relay-state 0 maybe   # rejected by argparse
```

Accepted: `on`/`off`, `true`/`false`, `1`/`0`, `yes`/`no`, `enable`/`disable`.

This is not stylistic. `bool("off")` is `True` in Python, and a CLI passes
strings — so a boolean parameter routed through `type=bool` would energise on
*every* spelling, including the ones that mean no. The PDU driver's
`isinstance(on, bool)` guard would catch the resulting non-bool, but a CLI that
is only safe because a driver three layers down is defensive is not safe.

## Why a one-shot needs its own lifecycle

A shell command opens a device, makes one call, and exits inside a second. An
MCP server does not, and four things follow that reflection cannot infer. They
live in [`cli_lifecycle.py`](../src/benchctrl/cli_lifecycle.py).

**Teardown depends on the mode.** Locally, the driver's `*_close` tool. Remotely,
`close()` is *refused* by the proxy, because closing is governor-mediated so an
armed output is never orphaned — the correct exit is a clean client disconnect,
which the agent reads as consent to release the writer claim. `agent.close` is
**not** the remote equivalent: it trips the governor bench-wide, so one command
finishing would drive every armed device on the bench to its safe state,
including instruments the command never touched.

**A one-shot must not disarm what a previous one armed.** `adu218_open` defaults
`disarm_watchdog=True`, and its connect path sends `WD0`. That default is right
for a long-lived server — the watchdog setting reads 0 both for "timed out" and
"never enabled" (§F-22), so a fresh session cannot interpret an inherited value
— and wrong here, because *every* invocation is a fresh session. Left alone:

```bash
benchctrl --yes adu218 set-watchdog 3   # arms it
benchctrl adu218 relay-states           # a read — and it disarms the watchdog
```

The CLI overrides the default to `False`. The driver is unchanged; its default is
correct for its other caller.

## Concurrency: one process at a time, per device

Two invocations against the same remote device do not queue. The claim is taken
at open, before the tool runs, and the loser fails immediately:

```
benchctrl error: PolicyError: otii_arc is claimed by session s-1; this session
is a read-only observer until it is released
Another session holds the writer claim on this device — most likely a second
benchctrl process or a dashboard that attached first.
Concurrent invocations fail immediately: the claim is taken at open, before the
tool runs, and nothing retries or queues. Nothing has been sent to the device.
Wait for the other process to exit, or run the command there.
```

Nothing retries and nothing backs off, so "wait" is the whole of the advice.
Recordings and streams cannot span invocations either — for anything stateful,
use the Python API.

## How this is verified

Three hardware-free modules cover the generated surface in-process:
`test_cli_generated.py`, `test_cli_main.py` and `test_cli_tiers.py` — 140 tests,
including the completeness assertion that fails the suite if a tool ships without
a tier.

[`test_hardware_cli.py`](../tests/test_hardware_cli.py) covers the two claims
those cannot make, because both are properties of *a process against a device*:
that a reflected subcommand really drives the instrument through a cold
open/call/teardown, and that the exit codes are what `$?` sees rather than what
`main()` returned.

The pairing that matters there is the gate. A refusal proves nothing on its own —
a permanently-closed gate passes every refusal assertion — so the satisfied case
is checked against real hardware too, where it must reach the device and exit 0.
With nothing attached it would exit 2, and 2-vs-3 would stop being a distinction.

```bash
# on the bench machine — the tests spawn a real `python3 -m benchctrl`
pytest -m hardware tests/test_hardware_cli.py -q
BENCHCTRL_CLI_HW_WRITE=1 pytest -m hardware tests/test_hardware_cli.py -q
```

The two relay-switching tests skip without that variable. The CLI has no
`allowed_relays` flag (see [Arguments deliberately not
exposed](#arguments-deliberately-not-exposed)), so a CLI write reaches whatever
relay is named — the nomination has to come from the operator, and it shares
`BENCHCTRL_ADU218_RELAY` with the driver's own hardware tests so the two files
cannot drift about which contact is safe to move.

## Known limits

- **There is no local governor.** `SafetyGovernor` is a member of the *agent
  server*; nothing in the CLI or the drivers constructs one. So a local one-shot
  has no arm tracking and no deadman, while remote mode has both. For the two
  switching devices this is tolerable and deliberate: the ADU218's protection is
  its own hardware watchdog, and the PDU is exempt from arm tracking by design
  (a deadman countdown on every switch would trip while an operator was at
  lunch). It is worth knowing that `benchctrl --local` gives you less protection
  than `--remote`, not more. The exposure is the Arc and the two Rigols, the
  devices a governor would actually be tracking; `KNOWN_LIMITATIONS.md` § A-6
  has the per-device breakdown.
- **A bare exit releases the claim but does not close the device** on the agent.
  Benign — with nothing armed the deadman never reclaims it either — but the CLI
  does not pretend otherwise.
- **`benchctrl` and `benchctrl arc` overlap** for the ten legacy commands, and
  the legacy ones ignore `--sim`/`--remote`.
- **The ADU218's relays are 1 A signal switches** despite the 120 V rating
  (§H-6). `benchctrl --yes adu218 set-relay-state` is not a way to switch a
  load; the PDU is.
- **Mains switching is now one shell line.** The bench cannot cut power to its
  own agent host only because of a cabling invariant — the Uno Q and the network
  gear are not on the PDU (`drivers.md`). That was already true; a mains-capable
  CLI raises the cost of it ever changing, because it becomes possible to
  destroy the recovery path in one command. `allowed_outlets` and
  `panic_outlets` are the controls to revisit *before* any such move
  (`KNOWN_LIMITATIONS.md` § F-12).
